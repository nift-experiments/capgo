## Earlier provider scaffold

`runtime/server.mjs` and `config/capabilities.json` expose a separate allowlisted provider contract (`/api/plans`, `/api/credits`, `/api/metrics`, `/api/rankings`, `/api/contact`). It can use recorded plans/credits or a configured `CAPGO_PROVIDER_URL`/server-only token. It does **not** transparently reconnect the faithful frontend, which still calls the original configured API base and signing routes. The earlier `RUNTIME-CONTRACT.md` describes that scaffold; its statements that the browser requests same-origin capability endpoints do not describe the faithful production controllers. Do not use scaffold contract tests as evidence that original sign-up/signing/pricing integrations work.

Reconnecting a user-owned backend requires implementing the original routes/schemas and runtime configuration, or a separately verified controller adaptation. Those are explicit residual limitations here. Retaining the frontend establishes reproducible migration fidelity, not self-contained backend completion.
